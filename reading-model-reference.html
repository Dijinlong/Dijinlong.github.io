Reading a model reference page: what billing unit, tier and channel actually mean

Published 2026-11-26 · LONG AI Engineering Notes · snapshot 2026-11-26 19:02 UTC+8

Most price mistakes are not arithmetic mistakes. They are reading mistakes: a number is copied from a reference page, the unit behind it is not, and a request that should cost cents gets budgeted as if it cost dollars. The page does not usually lie. It just packs three independent facts into one line — the billing unit, the price tier, and the channel that serves the request — and leaves you to separate them.

This note takes the three apart, using the current public snapshot of a model reference page: 109 live entries (81 text, 17 video, 11 image) and 563 documentation pages, read at 2026-11-26 19:02 UTC+8. Every entry on the page has the same shape, which is exactly why the fields are easy to swap.

One line of text, three different questions

A line that reads gpt-6-sol · input 0.012 / 1K tokens · output 0.036 / 1K tokens answers three questions that have nothing to do with each other:

  • Unit — 0.012 of what, per how much? Per 1K tokens, per 1M tokens, per image, per second?
  • Tier — is that the headline price, or one step on a staircase that only applies above a spend level?
  • Channel — which upstream produced this number, and is it the one that will actually serve your request?

Read the wrong unit and you are off by 1000×. Read the wrong tier and you are off by the discount percentage. Read the wrong channel and the price is right but the latency, the quota and the retry behaviour are somebody else's problem.

Billing unit: tokens, seconds, or a flat count

The 109 entries split by what they meter: 81 text entries bill on tokens, 17 video entries bill on seconds of generated output, and 11 image entries bill per image. A text entry is further split into input and output rates, and those two are never the same number. Inputs are usually repriced at a lower rate on a cache hit; outputs are not.

Watch the multiplier prefix. A page that says per 1K and another page that says per 1M can show numbers that differ by three orders of magnitude while describing the same price. When you copy a number into a spreadsheet, copy the unit beside it in the same cell, or the sheet will silently compare two different currencies of tokens.

Video and image entries meter the artifact, not the conversation: a clip is billed by output duration, so a re-roll costs real money.

Tier: a price table is a staircase, not a number

On the current snapshot, the entries that carry an ask-price structure do not carry one price each — they carry a ladder. Measured across all entries: 17 sit at a 50% step, 20 at 90%, 39 at 95%, and 33 go deeper than 95%. That distribution is the honest shape of the market: a headline rate and a negotiated rate are different fields on the same page.

Two rules follow. First, a tier is usually cumulative within a period, not per-order, so the price of your 40th request depends on the 39 that came before it. Second, the tier attaches to the seller, not to the model: two entries for the same model name can sit on different ladders. Numbers by model alone will therefore overstate or understate your bill.

The per-model prices and their current tiers are published on the live pricing table; the ladder depth per entry is what the table's second column is for.

Channel: who actually serves the request

Channel is the field people skip, and it is the one that decides whether the other two mean anything. A model name can appear under several sellers at once. In the current snapshot, 58 of 109 entries have exactly one seller behind them, 16 have two, and the rest spread across three or more — the widest entry has 15. Certification is not uniform either: 193 certified sellers are spread across 106 entries, which leaves 3 entries with no certified seller at all.

That matters concretely. Where several sellers compete on one model, the effective price is the cheapest on-call seller; where only one exists, the listed price is the only price. The seller-count distribution is on the model plaza.

A worked example on one reference entry

Take one text entry and read it field by field rather than as a price:

The failure mode is reading the row as one sentence — "0.012 per 1K, 95% off, one seller" — and multiplying all three numbers together.

Normalise before you compare

The cheapest fix is to stop comparing raw numbers and compare a normalised rate. The function below takes a reference line and returns a cost per million output tokens, which is the only figure that is comparable across text entries. It does no network calls, so it runs against a saved snapshot.

RATE = {"1k": 1_000, "1m": 1_000_000}

def per_million(rate_str):
    # "0.036/1K" or "36/1M" -> cost per 1M of the same unit
    rate, unit = rate_str.split("/")
    rate, unit = float(rate), unit.strip().lower()
    per = RATE[unit]
    return round(rate * (1_000_000 / per), 3)

def entry_cost(entry, tokens_out=1_000_000):
    out = per_million(entry["output_rate"])
    step = entry.get("tier_percent_off", 0) / 100
    return round(out * (1 - step), 3)

sample = {"output_rate": "0.036/1K", "tier_percent_off": 50}
print(entry_cost(sample))   # 18.0

Two things matter more than the printed numbers: the unit is explicit in the input string, and the tier is applied once, at the end.

Five checks before you quote a price

  1. Write the unit next to every number, including the prefix (1K vs 1M).
  2. Split input and output rates; cache-hit pricing is a third rate again.
  3. Ask whether the tier is per period or per order, and whether it belongs to the model or the seller.
  4. Record the seller count beside the price — a single-seller entry has no fallback bid.
  5. Snapshot the page with a timestamp; the 563 documentation pages on model docs and the price table change independently, and mixing snapshots is the quietest way to get a wrong total.
