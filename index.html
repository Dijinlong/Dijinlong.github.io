LONG AI engineering notes: 103 models, 51 upstream sellers, one OpenAI-compatible endpoint

Published 2026-11-21 · LONG AI

A single /v1/chat/completions request looks trivial from the client side. Behind it sit five stages: auth and quota, model-name normalisation, upstream selection, protocol adaptation, and streaming plus usage accounting. These are the notes from routing live traffic through 51 upstream sellers.

Routing: the same model id is not the same product

Behind the same model id, different upstreams ship different versions, different context windows and sometimes different billing units. We tag every upstream model with capability flags — context length, tool-calling support, image input — and rank stability above price when choosing a route. Channels discounted below 20% of list price usually carry an order-of-magnitude worse timeout rate, and the savings get eaten by retries.

Billing: pre-hold, settlement, refund — in which order

  • Hold an upper-bound estimate when the request arrives.
  • Settle against the real usage the upstream returns, input and output priced separately.
  • Refund in full on failure, including the intermediate state where the upstream was charged but returned no content.

Get that order wrong and users see "balance dropped but no answer" — the fastest way to lose a customer.

Protocol compatibility: a 200 does not mean it works

An upstream that returns 200 may still stream incorrectly; one that streams fine may violate the spec on tool_calls. We run a fixed regression suite against every channel: chunk format, finish_reason, usage fields, and whether error codes land inside OpenAI semantics. A channel that fails this suite never enters the primary lane, however cheap it is.

Three concrete traps

Across 51 sellers the most common defects are self-invented error codes (rate limits reported as 500), missing usage at stream end, and silent context truncation. The third is the nastiest: the request succeeds, the answer looks reasonable, and the tail was quietly dropped.
